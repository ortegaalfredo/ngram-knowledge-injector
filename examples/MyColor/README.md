# MyColor — a minimal end-to-end color-injection example

The smallest possible complete demo of the whole pipeline: one knowledge entry,
one overlay build, one HTTP request. It teaches the model to complete the
prompt `My color is` with a **chosen color**, purely by writing vectors into the
PLE n-gram table — no fine-tuning, no GGUF rewrite.

The punchline: the injected vector is `"vector": "random"` with a `seed`, and
**the seed deterministically picks the color**. Empirically (see the `note` in
[`MyColorIs-Patch.json`](MyColorIs-Patch.json)):

| seed | model says |
|---:|---|
| 1  | white |
| 14 | red |
| 23 | purple |
| 25 | black |
| 48 | (not a color) |

That makes this example a good intuition pump for what the PLE table is: a
hash-addressed associative memory whose 160-d rows are dense with
concept-adjacent directions, so a *seeded random vector* behaves like a key you
can turn to select a behavior.

## Files

| File | Role |
|---|---|
| [`MyColorIs-Patch.json`](MyColorIs-Patch.json) | The knowledge file: one entry — trigger `"My color is"`, seeded random vector, `op: blend`, `alpha: 0.8`, `at: "all"`. Change `seed` to change the color. |
| [`inject.sh`](inject.sh) | Builds the sidecar overlay `./model/MyColorIs.plepatch` from the knowledge file via [`../../inject.py`](../../inject.py) (`--mode overlay`). Never touches the GGUF. |
| [`request.sh`](request.sh) | Greedy single-token probe: `POST /v1/completions` with prompt `"My color is"`, `max_tokens: 1`, `temperature: 0`, `seed: 0` — the response token *is* the injected color. |
| `./model/MyColorIs.plepatch` | *(generated by `inject.sh`)* the overlay: row ids + raw Q8_0 bytes + manifest. |

## How the injection works

1. `inject.py` tokenizes the trigger exactly like llama.cpp would
   (`My` ` color` ` is`), and for **each token position** computes the 16 PLE
   rows the runtime hashes that context into (8 bigram + 8 trigram heads).
   `at: "all"` is why every position is armed, not just the last one — the
   signal then fires no matter which prefix of the trigger is being scored.
2. Each of those rows is replaced 80 % by the seeded gaussian vector
   (`blend`, `alpha: 0.8`) — a strong push, appropriate because the rows only
   affect contexts that hash to them (collisions are reported and blended by
   [`../../inject.py`](../../inject.py)).
3. At inference the patched rows are mapped in memory over the read-only GGUF
   (copy-on-write, via `llama_patch/ple-overlay.patch`), get added to the
   residual stream whenever `My color is` appears, and nudge the next token to
   the color that the seed's direction points toward.

Why a *random* seed gives a *stable* color: the 160-d per-layer-input space is
packed with learned structure; a fixed gaussian draw lands in a fixed place,
and that place happens to sit near "whiteness", "redness", etc. in a way that
reproduces run to run. Seed 48 is a nice control: its direction is not near any
color concept.

## Running it

Prerequisites:

- GGUF shards at `./model/Qwen3.8-Flash-Next-Q8_0-00001-of-00006.gguf`
  (see the repo-root [`README.md`](../../README.md) for where they go).
- A llama.cpp **fork** built with
  [`llama_patch/ple-overlay.patch`](../../llama_patch/ple-overlay.patch)
  (needed for `LLAMA_PLE_OVERLAY` support).

```bash
# 1. build the overlay (tiny, seconds). NOTE: the paths in inject.sh are
#    relative — run it from a directory where ./inject.py, ./model/ and
#    ./MyColorIs-Patch.json all resolve (e.g. symlink the patch file into a
#    repo-root checkout, or edit the paths).
bash examples/MyColor/inject.sh

# 2. serve with the overlay applied at load time
LLAMA_PLE_OVERLAY=$PWD/model/MyColorIs.plepatch \
  <llama.cpp-fork>/build/bin/llama-server \
  -m ./model/Qwen3.8-Flash-Next-Q8_0-00001-of-00006.gguf --port 8080
# look for: "apply_ple_overlay: applied N PLE overlay row(s)"

# 3. ask (greedy, so the answer is deterministic)
bash examples/MyColor/request.sh
```

Expected response: the completion token is the seed's color — with the shipped
`seed: 1`, `white`.

To try another color, edit the `seed` in `MyColorIs-Patch.json`, re-run
`inject.sh`, restart the server (or use the overlay-reload path described in
[`plans/ple-overlay-reload.md`](../../plans/ple-overlay-reload.md)), and probe
again.

## Gotchas

- **Exact trigger match required.** `request.sh` uses the raw
  `/v1/completions` endpoint with the prompt byte-identical to the trigger. A
  chat-template wrapper changes the tokens — and therefore the hashed rows —
  and the injection silently misses.
- **Overlay naming.** The output `MyColorIs.plepatch` is *not* the
  auto-discovered sibling name (`<shard>.gguf.plepatch`), so you must set
  `LLAMA_PLE_OVERLAY` explicitly.
- **Greedy decoding.** `temperature: 0` + fixed `seed` is what makes the color
  reproducible; sampling can wash out a weaker push.
- **Rows are shared.** The 16 rows also serve whatever other n-grams collide
  on them; with `alpha: 0.8` those contexts get the same nudge. Check the
  collision report printed by `inject.sh` (or add `--dry-run`) if you care.
